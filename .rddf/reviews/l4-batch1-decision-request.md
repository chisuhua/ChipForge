## A. 5 个缺口（★ 逐条含实测依据 + 建议）

### G1 — 门禁 ①④ 的**判据文字**在台账中缺失

| 项 | 内容 |
|---|---|
| **事实** | `.rddf/reviews/ADR-094-decision-ledger.md` D-17④ 只给了 5 条门禁的**强度**（① 硬 · ④ WARN「先看噪声」），**没写 ① 与 ④ 检查什么** |
| **影响** | ①④ 的验收判据无依据 ⇒ 实施者只能猜 ⇒ 判据不可机检 |
| **★ 我的推断**（写在 `design.md` §4） | **①** = 层 2 单元 MUST 经 `root.create_child`（禁裸 `make_unique`）· **④** = root 名 / 端口前缀硬编码（如 `top__DOT___reg_N`、`--top-module top`） |
| **建议** | ✅ **采纳该推断**并写进 ADR-094 §D-3.7（★ 现有代码事实与之吻合：§2.1 的 #1 / #12 / #13 / #14 正是这几类） |

### G3 — ★ 生产代码里**零 `declare_out` 调用** ⇒ ①-D owner 切换后**测试批量变红**

| 项 | 内容 |
|---|---|
| **事实** | ADR-094 r.6 要求「顶层端口 MUST 经 `PipeBuilder::declare_in/out` 创建」⇒ ★ 但生产代码（`ip/**` / `src/**`）里**没有任何 `declare_out` 调用** ⇒ 只有 20+ 个**测试**调用点（`tests/cpu/test_cpu_open_core_*.cpp`） |
| **★ 后果** | ①-D 的 owner 切换后，节点名从 `open_pc` ⇒ `cpu.open_pc` ⇒ ★ **这批测试的端口名断言会批量变红** ⇒ ★ **ADR-094 未覆盖测试基线的处置方式** |
| **选项** | **(a)** 改断言（承认新命名）★ **(b)** 改端口名（让顶层端口保持裸名，与 D-3.4 冲突）★ **(c)** 测试改走 manifest/契约名解析（最正，但工作量最大） |
| **建议** | ✅ **(a) 改断言** + ★ **在 ①-D 之前先摸底**：★ 实施前先跑一次「owner 切换的 dry-run」统计到底有多少测试断言受影响 ⇒ ⇒ 再决定逐条改还是改断言写法 |

### G5 — r.14 无「**创建时机维度**」

| 项 | 内容 |
|---|---|

## B. 3 条物理事实（★ 建议已给出，★ 只需点头）

| # | 问题 | ★ 建议 | 依据 |
|---|---|---|---|
| ① | root 的持有类型 | **`std::shared_ptr<ch::Component>`** | ★ 上游 `create_child` 内部 `make_shared` + 依赖 `weak_from_this()`；`add_child` 收 `unique_ptr` 转 shared ⇒ root 必须 shared_ptr 才能 `create_child` |
| ② | root 构造是否复用 `ConstructionFrame` | **必须复用** | ★ 上游 `ch_device` 先例 `CppHDL/include/device.h:24-27`（★ ADR-094 引用的正是这行）⇒ 否则 root 自己的 `ch_reg` / 端口归错层 |
| ③ | `top_module_name`（`top`）与 root 实例名（`cpu`） | ★ **两个不同常量，MUST NOT 混**；★ **模块名保持 `top` 不变**（D-4：门禁消费扁平 `top.v`） | ★ 后果 = 顶层端口名 `reg_1` ⇒ `cpu_reg_1` ⇒ 这就是 ①-D 必须同批改 `sim_main.cpp` 的根因 |
