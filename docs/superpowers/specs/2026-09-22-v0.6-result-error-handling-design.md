**日期**: 2026-09-22

**目标版本**: ChipForge v0.6.0
**关联**: P1 缺口修复（Phase 6d 验证报告 [2026-09-22-v0.5.0-phase6d-closeout](../../.omo/architecture-reviews/2026-09-22-v0.5.0-phase6d-closeout.md) 标记的唯一 Critical 项）

## 1. 背景与动机

### 1.1 P1 缺口定义

ChipForge v0.5.0 (Phase 6d 收官) 的架构验证报告标记了**唯一 Critical P1 项**：

> **问题 #1**: ChipForge 应用层错误处理缺失
> - **现象**: CppHDL 267 处 `CHERROR/assert`；`include/cf/plugin/*.h` 0 处结构化错误
> - **影响**: SoC 级调试时缺少 IP 失效传播链，故障定位依赖 gdb + log 跟踪

具体表现为：
- 框架头文件 `include/cf/plugin/pipe_builder.h` 中 8 处 `throw std::invalid_argument` + 3 处 `throw PluginException`
- `include/cf/plugin/payload.h` 中 6 处 `throw std::runtime_error`（CH_MEM fail-fast）
- 业务代码 `include/cpu/cpu_factory.h` 中 2 处 `throw std::invalid_argument`
- 静态配置期 API 几乎全部 `void` 返回，错误只能通过异常上抛或 nullptr 隐式传播

### 1.2 为什么必须修

- **CH_MEM elaboration 路径阻塞**: `std::expected<T,E>` 是值类型，可穿透 lnode DAG 边界；`throw` 在 elaboration 路径不可重入
- **配置错误应当 fail-fast 在配置期**，不应延后到仿真启动后
- **CppHDL 已是 C++23**，主项目仍 C++17 已成为技术债

### 1.3 为什么 v0.6 而不是 v0.7+

v0.5.0 刚刚收官，Phase 6d 闭环（Verilator E8 cycle-identical）。v0.6 是 Phase 6e（应用层强化）的自然起点；不开新 branch，不阻塞主线。

## 2. 目标与非目标

### 2.1 目标

1. 主项目 `ChipForge` + `cf_plugin` INTERFACE 库 + 单元测试目标升级到 **C++23**
2. 静态配置期 API（10 个 P0）从 `void` + `throw` 迁移到 `std::expected<T, PluginError>` 值类型
3. 新增 `enum class PluginError` 错误类型 + `plugin_error_message()` 工厂
4. `CpuFactory::build_cpu()` 内部 Result 化，对外保留 throw 包装层（兼容现有 `cpu_sim/main.cpp` 入口）
5. 新增 ADR-047 + 现有 ADR-026/030/031/032 补 Result 路径
6. 新增 CI Check 10/11/12 防止未来回退
7. 工作量控制在 **24 小时**（3 人/天 或 1 人/周）

### 2.2 非目标（Out of Scope，v0.7+ 处理）

- ❌ CppTLM (C++17 子仓库) 不升级
- ❌ CppHDL (C++23 子仓库) 不动

- ❌ `PipeBuilder::run()` 保留 throw（CtrlLink `throw_when` 运行时语义）
- ❌ `at_stage` 注册的回调函数体内部仍可 throw
- ❌ 16 个业务 plugin 的 at_stage 调用点暂不改（P2 阶段）
- ❌ 53 个测试断言 `REQUIRE_THROWS_*` 改写（P2 阶段，独立 PR）
- ❌ CH_ASSERT 宏替换（CppHDL 子仓库）

## 3. 设计方案

### 3.1 架构：C++23 升级边界

```
┌──────────────────────────────────────────────────────────────┐
│ 主项目 ChipForge (v0.6 升 C++23)                              │
│   ├─ CMakeLists.txt                CMAKE_CXX_STANDARD 23     │
│   ├─ src/cf_plugin/CMakeLists.txt  INTERFACE cxx_std_23      │
│   └─ tests/CMakeLists.txt          cxx_std_23 (×2 targets)   │
└────────────────┬─────────────────────────────────────────────┘
                 │ 链接 (C 链接兼容层 + Itanium ABI)
                 ↓
┌──────────────────────────────────────────────────────────────┐
│ CppTLM (子仓库, 不动)        CppHDL (子仓库, 不动)            │
│   C++17 ABI 静态库             C++23 ABI 静态库               │
│   libcpptlm_core.a             libcpphdl.a                   │
└──────────────────────────────────────────────────────────────┘
```

**关键**：
- GCC 13.3.0 在 `_GLIBCXX_USE_CXX11_ABI=1` 一致下，C++17 ↔ C++23 ABI 兼容
- `cf_plugin` 是 INTERFACE 库（头文件 only），`cxx_std_23` 自动传播到所有依赖 cf_plugin 的 target
- CppHDL 已是 C++23（实测 `set(CMAKE_CXX_STANDARD 23)`），无需修改

### 3.2 静态/动态 API 边界（D4 增强）

| 阶段 | API 风格 | 错误传播 | 理由 |
|------|----------|----------|------|
| **配置期**（`build()` 前） | `Result<T>` = `std::expected<T, PluginError>` | 值类型 | CppHDL elaboration 路径必须可重入 |
| **构建期**（`build()` 内） | `Result<T>` | 值类型 | 单次调用，可恢复 |
| **Elaboration 期** | `Result<T>` | 值类型 | 同上 |
| **运行期**（`run()` tick 循环） | `void` + throw | `PluginException` | CtrlLink `throw_when` 是运行时语义 |

### 3.3 组件设计

#### 3.3.1 新增 `include/cf/plugin/plugin_error.h` (~120 行)

```cpp
namespace cf::plugin {

// 错误枚举（20 字段）
enum class PluginError {
  // ── 参数校验（10 个，迁移自 std::invalid_argument）──
  NullPlugin, NullCallback, NullCommitHook, NullCtrlLink,
  NullConnector, EmptyStageName, EmptyParentStageName,
  NullContextPtr, CtxNotProvided, AlreadyElaborated,
  // ── 配置冲突（4 个）──
  DuplicatePlugin, DuplicateStageName,
  UnknownStage, StageNotFound,
  // ── 构建/elaboration（5 个）──
  BuildFailed, PluginBuildFailed,
  ElaborationFailed, ConnectorFailed,
  UnsupportedPipelineDepth, UnsupportedMulLatency,
  // ── 运行期/P2 保留 throw（供 catch 匹配）──
  ThrowConditionTriggered,
  PayloadCellMissing, PayloadTypeMismatch,
};

// Result 别名
template <typename T>
using Result = std::expected<T, PluginError>;

// 错误消息工厂（替代 PluginException::what()）
inline std::string plugin_error_message(PluginError err,
                                         const std::string& detail = "");

// PluginError → PluginException 转换（保留 throw 兼容性）
PluginException to_exception(PluginError err,
                              const std::string& stage = "");

}  // namespace cf::plugin
```

#### 3.3.2 新增 `include/cf/plugin/result_macros.h` (~30 行)

```cpp
// 内部传播宏（PipeBuilder 内部失败快速返回）
#define PB_TRY(expr)                                                     \
  do {                                                                   \
    if (auto _r = (expr); !_r) return std::unexpected(_r.error());        \
  } while (false)

// 条件检查宏
#define PB_EXPECT(cond, err)                                             \
  if (!(cond)) return std::unexpected(err)

// 业务侧抹平工具（cpu_sim/main.cpp 入口）
template <typename T>
T auto_throw(Result<T> r) {
  if (!r) throw to_exception(r.error());
  return std::move(*r);
}
```

#### 3.3.3 增强 `include/cf/plugin/plugin_exception.h`

- 类签名不变（保持向后兼容）
- 新增构造函数：`PluginException(PluginError err, std::string stage = "")`
- 现有 `runtime_error(message)` 构造路径保留

#### 3.3.4 PipeBuilder 12 个 P0 API 签名变化

| API | Before | After | 内部 throw 原位置 |
|-----|--------|-------|-------------------|
| `register_plugin` | `void` | `Result<void>` | `throw std::invalid_argument("plugin is null")` |
| `at_stage` | `void` | `Result<void>` | 2 throws (empty name, null cb) |
| `declare_substage` | `void` | `Result<void>` | 新增 `EmptyParentStageName` 校验 |
| `register_commit_hook` | `void` | `Result<void>` | `throw std::invalid_argument` |
| `register_ctrl_link` | `void` | `Result<void>` | 2 throws |
| `register_stage_payload_connector` | `void` | `Result<void>` | 2 throws |
| `build` | `void` | `Result<void>` | 新增 try-catch 包装 plugin callback |
| `elaborate(ctx)` / `elaborate()` | `void` / `void` | `Result<void>` | `throw PluginException("ctx_ is null")` |
| `to_verilog` | `void` | `Result<void>` | 同上 |
| `create_simulator` | `unique_ptr<Simulator>` | `Result<unique_ptr<Simulator>>` | 同上 |

**P1 附带**：
- `node_of_logic_stage(name)` 从 `nullptr` 改为 `Result<shared_ptr<PipeNode>>`（消除隐式错误）
- `get_ctrl_link(name)` 从 `nullptr` 改为 `Result<shared_ptr<CtrlLink>>`

### 3.4 数据流

#### 3.4.1 配置期错误传播（Result 范式）

```cpp
// 内部实现 (P1 改造后)
Result<unique_ptr<PipeBuilder>> CpuFactory::build_cpu_impl(
    const CpuConfig& config, Memory& mem) {
  auto pb = make_unique<PipeBuilder>();

  PB_TRY(pb->register_plugin(make_unique<IBusPlugin<U>>(mem)));
  PB_TRY(pb->register_plugin(make_unique<DBusPlugin<U>>(mem)));
  // ... ~7 plugins 全部 PB_TRY

  PB_TRY(pb->at_stage("Fetch", Phase::NORMAL, fetch_cb));
  // ... ~80 at_stage 调用全部 PB_TRY

  PB_TRY(pb->register_commit_hook(commit_cb));
  PB_TRY(pb->build());

  for (auto& [stage, ctrl] : config.ctrl_links) {
    PB_TRY(pb->register_ctrl_link(stage, ctrl));
  }

  if (config.enable_mmu) {
    PB_TRY(pb->register_stage_payload_connector<...>(...));
    PB_TRY(pb->elaborate(ctx));
  }
  return pb;
}

// 对外保留 throw 包装层 (P1 期间不破 API)
unique_ptr<PipeBuilder> CpuFactory::build_cpu(const CpuConfig& config, Memory& mem) {
  auto r = build_cpu_impl(config, mem);
  if (!r) throw to_exception(r.error(), "CpuFactory::build_cpu");
  return std::move(*r);
}
```

#### 3.4.2 运行期错误传播（保留 throw，不变）

```cpp
// PipeBuilder::run() 不变
void PipeBuilder::run() {
  while (/* ... */) {
    for (auto& [stage, cl] : stage_ctrl_links_) {
      if (cl->should_throw()) {
        throw PluginException(stage, "throw_condition_triggered");
      }
    }
    // ... tick 循环
  }
}
```

测试中 `REQUIRE_THROWS_AS(pb.run(), PluginException)` **不需改**。

## 5. 风险评估与缓解

| # | 风险 | 概率 | 影响 | 缓解措施 |
|---|------|------|------|---------|
| R1 | C++17→23 升级导致 GCC 13.3 边缘特性问题 | 10% | 高 | 先独立分支升级 + 全量 ctest 验证；GCC 13 C++23 已生产级 |
| R2 | CppTLM (C++17 ABI) 与 C++23 父项目的 inline 模板冲突 | 15% | 中 | `_GLIBCXX_USE_CXX11_ABI=1` 一致保证；如出问题 CppTLM 头文件加 visibility pragma |
| R3 | 109 个业务调用点编译失败（结果丢弃警告） | 30% | 中 | 利用 `[[nodiscard]]` 编译器警告自动发现 |
| R4 | `pb.build()` 内部 plugin 回调 throw 被短路 | 25% | 中 | try-catch 包装：(a) PluginException → PluginBuildFailed；(b) std::exception → 通用错误 |
| R5 | `at_stage` 回调内部 `PayloadStore::get()` 仍 throw，与 Result 不统一 | 80% | 低（设计约定） | ADR-047 例外清单明确记录；超出本迁移范围 |
| R6 | `cpu_sim/main.cpp` 调用点遗漏 | 20% | 低 | `auto_throw()` 抹平工具；CPU simulator 单测验证 |

### 性能影响

**零**。迁移范围是静态配置期 API（`register_*` / `build` / `elaborate` / `to_verilog`），每个程序生命周期调用一次或几次。`std::expected` 开销（一次分支预测 + Error 枚举拷贝）在此上下文可忽略。热路径（`run()` tick 循环）不变。

### ABI 兼容性

- `cf_plugin` 是 INTERFACE 库（头文件 only），无 ABI 问题
- `libcpptlm_core.a` C++17 ABI 通过 C 链接兼容层 + Itanium ABI 一致保证
- `libcpphdl.a` 已是 C++23 ABI，一致

## 7. ADR 与文档

### 7.1 新增 ADR-047

`docs/architecture/adr/ADR-047-static-config-result-paradigm.md` (~80 行)：

```markdown
# ADR-047: 静态配置期错误处理采用 Result 范式

## 状态
Accepted (v0.6.0, 2026-09-22)

## 上下文
cf::plugin 框架的静态配置 API（pb.build() 之前的 register_*/at_stage/build/elaborate/to_verilog）
当前全部 void + throw，与 CppHDL elaboration 路径不可重入冲突。

## 决策
所有静态配置 API 必须返回 std::expected<T, PluginError>。

## 例外
1. PipeBuilder::run() 的 CtrlLink throw_when —— 运行期语义
2. PayloadStore::get() —— at_stage 回调内热路径
3. CppHDL 子仓库的 CH_ASSERT —— 范围外
4. PluginBase 虚函数（setup/build）—— 回调体内部业务代码可自由选择

## 理由
- CH_MEM elaboration 路径需要值类型错误传播
- 静态配置错误应在配置时 fail-fast
- 与 CppHDL 的 C++23 标准对齐

## 迁移
- P0: C++23 升级 + 12 API 签名改
- P1: cpu_factory 内部 Result 化 + ADR 同步 + CI 检查
- P2 (v0.7+): 业务代码全量适配 + 53 测试断言改写
```
